# ขั้นตอนมาตรฐานการพัฒนาและทดสอบคุณภาพซอฟต์แวร์ (Software Development & QA SOP)
## รหัสเอกสาร: REG-QA-SOP-002 | เวอร์ชัน: 1.0 | วันที่ประกาศใช้: 30 สิงหาคม 2026

---

## 1. วัตถุประสงค์ (Purpose)
เพื่อกำหนดขั้นตอนปฏิบัติในการพัฒนา เขียนโค้ด ตรวจทาน (Code Review) และทดสอบคุณภาพ (Testing) สำหรับโครงการ **Smart Event Registration** เพื่อให้แน่ใจว่าซอฟต์แวร์ที่พัฒนาขึ้นมีความปลอดภัย เสถียรภาพ และสอดคล้องตามข้อกำหนดของพระราชบัญญัติคุ้มครองข้อมูลส่วนบุคคล (PDPA) รวมถึงเป็นระเบียบการจัดหาซอฟต์แวร์คุณภาพระดับ ISO 9002

## 2. ขั้นตอนการวงจรชีวิตการพัฒนา (Development Lifecycle Stages)

```
[วิเคราะห์ความต้องการ] ➔ [วางสถาปัตยกรรม & DB] ➔ [เขียนโค้ด (Coding)] ➔ [ตรวจทานโค้ด (Review)] ➔ [ทดสอบระบบ (QA Test)] ➔ [ติดตั้งใช้งาน (Release)]
```

## 3. ระเบียบการควบคุมซอร์สโค้ดและ Git Flow (Source Control & Branching Strategy)

*   **กิ่งหลัก (`main`)**: บันทึกโค้ดเวอร์ชันใช้งานจริง (Production-Ready) เท่านั้น ห้ามเขียนโค้ดลงในกิ่งนี้โดยตรง และจะอัปเดตผ่าน Pull Request อนุมัติแล้วจากกิ่ง `develop`
*   **กิ่งพัฒนา (`develop`)**: กิ่งสำหรับรวมผลงานพัฒนาทั้งหมดของทีม เพื่อเตรียมทำการทดสอบในห้องแล็บ QA (Staging Environment)
*   **กิ่งฟีเจอร์ (`feature/tkt-[รหัสงาน]`)**: กิ่งย่อยสำหรับแยกพัฒนาฟีเจอร์แต่ละส่วนตามที่ระบุใน Jira Backlog เช่น `feature/tkt-104-email-ticket`
*   **การรวมโค้ด (Pull Request Requirements)**:
    1.  ต้องผ่านการประเมินและรีวิวโดยโปรแกรมเมอร์ผู้อื่นอย่างน้อย 1 คน (Peer Review)
    2.  ต้องผ่านการคอมไพล์และการทดสอบ Unit Test 100% สำเร็จ
    3.  ต้องไม่มีข้อผิดพลาด Lint หรือช่องโหว่ความปลอดภัยระดับร้ายแรง (No Critical Security Vulnerability)

## 4. มาตรฐานและแนวทางการเขียนโค้ด (Coding Standard Guidelines)

เพื่อรองรับความเป็นระเบียบและให้ซอฟต์แวร์มีความยืดหยุ่นอ่านง่ายภายใต้มาตรฐาน ISO:
1.  **สไตล์โค้ด**: ใช้มาตรฐาน ESLint (แนะนำ Standard หรือ Airbnb Guideline) ร่วมกับ Prettier เพื่อจัดฟอร์แมตโค้ดอัตโนมัติ
2.  **การตั้งชื่อตัวแปรและฟังก์ชัน**:
    *   ภาษา JavaScript: ใช้ `camelCase` สำหรับตัวแปรและฟังก์ชันทั่วไป และ `PascalCase` สำหรับคลาสหรือคอมโพเนนต์
    *   ภาษา SQL: ใช้ `snake_case` สำหรับชื่อตารางและชื่อคอลัมน์ของฐานข้อมูล
3.  **ความปลอดภัยข้อมูล (Security)**:
    *   **SQL Injection Prevention**: ห้ามต่อสตริงคิวรี่ SQL ตรงๆ ในการเชื่อมต่อดาต้าเบส ให้ใช้ Parameterized Queries เสมอ
    *   **Data Masking**: ข้อมูลรหัสผ่าน บัญชีคีย์ SMTP หรือคีย์สำคัญส่วนบุคคล ห้ามฝังไว้ในซอร์สโค้ด ให้ดึงผ่าน Environment Variables (.env) เสมอ

## 5. แผนการทดสอบและการรับประกันคุณภาพ (QA & Testing Controls)

ระบบที่ส่งมอบต้องผ่านกระบวนการตรวจสอบคุณภาพ 3 ระดับ:

### 5.1 การทดสอบระดับย่อย (Unit Testing)
*   **เครื่องมือ**: ใช้เฟรมเวิร์ก `Jest` สำหรับประมวลผลทดสอบแยกส่วนของฟังก์ชัน
*   **เกณฑ์ผ่านการรับรอง (Metric)**: โค้ดในส่วน Business Logic และ Service Layer ต้องมีปริมาณความครอบคลุมของการทดสอบ (Code Coverage) ไม่ต่ำกว่า **80%**

### 5.2 การทดสอบระดับบูรณาการ (Integration & API Testing)
*   **เครื่องมือ**: ใช้ `Postman` หรือ `Supertest` เพื่อทดสอบยิง Endpoints API ในการอ่าน เขียน แก้ไข ข้อมูล และตรวจสอบการเชื่อมต่อ Database / Redis
*   **เกณฑ์ผ่านการรับรอง**: JSON Response Payload ต้องมีความสอดคล้องตามข้อกำหนดในเอกสารข้อกำหนด API ([api_spec.md](file:///Users/apirak.ba/Developer/booth_register/docs/api_spec.md)) 100%

### 5.3 บันทึกประวัติการทดสอบระบบ (Test Execution Log)
ทุกครั้งที่ตรวจรับมอบงานเพื่อออกเวอร์ชันใหม่ สตาฟควบคุมคุณภาพ (QA Tester) จะต้องบันทึกประวัติการทดสอบ ผลลัพธ์ วันเวลาที่ทดสอบ และชื่อผู้ทดสอบ ลงในระบบ Document Control กลาง เพื่อรองรับการเข้าตรวจประเมินของ Auditor เสมอ
