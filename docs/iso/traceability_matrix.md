# ตารางตรวจสอบย้อนกลับข้อกำหนดระบบ (System Traceability Matrix)
## รหัสเอกสาร: REG-QA-SPEC-001 | เวอร์ชัน: 1.0 | วันที่ประกาศใช้: 30 สิงหาคม 2026

---

## 1. คำอธิบาย (Introduction)
ตารางนี้จัดทำขึ้นเพื่อใช้เป็นหลักฐานยืนยันในกระบวนการประกันคุณภาพตามข้อกำหนด **ISO 9002** เพื่อให้แน่ใจว่า **ทุกข้อกำหนดความต้องการทางธุรกิจ (Requirements)** จากเอกสาร PRD ได้รับการนำไปออกแบบโครงสร้างข้อมูล (Database Schema) เขียนฟังก์ชันให้บริการ (API Endpoint) แสดงผลในหน้าจอผู้ใช้งาน (User Interface) และผ่านการทดสอบความถูกต้อง (Verification Cases) ครบถ้วนโดยไม่มีการตกหล่น

---

## 2. ตารางตรวจสอบย้อนกลับความต้องการ (Traceability Matrix)

| รหัสข้อกำหนด | รายละเอียดข้อกำหนด (PRD Requirement) | ตารางฐานข้อมูล (Database Schema) | เซิร์ฟเวอร์ API & WebSocket (Backend API / WS) | หน้าจอจำลองระบบ (User Interface / Tab) | กรณีทดสอบควบคุม (Verification Test Case) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **REQ-01** | **ระบบลงทะเบียนด้วยตนเอง (Online Registration)**:<br/>กรอกชื่อ, บริษัท, ตำแหน่ง, เมล, เบอร์ เพื่อสมัครเข้างาน | ตาราง `participants`<br/>(บันทึกรายชื่อผู้เข้าร่วมงาน) | `POST /api/v1/events/:event_id/register` | แท็บ **"พอร์ทัลมือถือ (Mobile Simulator)"** (Tab 9) | `Test-01`: กรอกฟอร์มลงชื่อบนมือถือจำลอง สำเร็จและเปลี่ยนเป็นหน้าตั๋ว |
| **REQ-02** | **ข้อตกลงความเป็นส่วนตัว (PDPA Consent)**:<br/>แสดงกล่องยินยอมและข้อความชี้แจงกฎหมาย PDPA | ตาราง `participants`<br/>(บันทึกการยินยอมตามขอบเขตข้อตกลง) | `POST /api/v1/events/:event_id/register`<br/>(ตรวจสอบ Checkbox = true) | แท็บ **"พอร์ทัลมือถือ"** (Consent Checkbox) | `Test-02`: ทดสอบกดสมัครโดยละเว้นการติ๊ก Consent (เบราว์เซอร์ต้องบล็อกไม่ให้ส่ง) |
| **REQ-03** | **ระบบจัดส่งตั๋วคิวอาร์โค้ด (QR Ticket & Mail)**:<br/>ออกรหัสคิวอาร์โค้ดตั๋วและยิงเมลเข้ากล่องจดหมายผู้สมัคร | ตาราง `participants`<br/>(คอลัมน์ `ticket_code` สุ่มรหัสตั๋ว) | `POST /api/v1/events/:event_id/register`➔ ทริกเกอร์ `sendTicketEmail` | หน้าจอมือถือแสดงบัตรคิวอาร์ (Wallet Card) และแสดง Log ลิงก์บน Terminal | `Test-03`: ตรวจสอบการส่งอีเมลตั๋วจำลองเข้ากล่อง Ethereal Mail ดูความสมบูรณ์ของ HTML |
| **REQ-04** | **การสแกนผ่านประตูทางเข้า (Fast Check-in)**:<br/>ยิงสแกนคิวอาร์ตั๋วผ่านประตูหน้างานอย่างรวดเร็ว | ตาราง `checkins`<br/>(บันทึกสิทธิ์การผ่านประตู และประวัติเข้างาน) | `POST /api/v1/checkin` (บันทึกเช็คอิน)<br/>`io.emit('participants:update')` (อัปเดตสตาฟ) | แท็บ **"จัดการข้อมูล (CMS)"** และปุ่มสแกนบนเครื่องมือถือจำลอง | `Test-04`: กดปุ่มจำลองการยิงสแกนตั๋วบนมือถือ ➔ เช็คสถานะเปลี่ยนสีเขียวและอัปเดต CMS ตาราง |
| **REQ-05** | **ป้ายไฟ LED ต้อนรับเรียลไทม์ (Welcome Signage)**:<br/>เมื่อมีคนสแกนผ่านประตู ให้โชว์ชื่อต้อนรับทันที | ตาราง `participants` & `checkins` | WebSocket Event:<br/>`welcome:new_checkin` (สตรีมชื่อผู้เข้างาน) | แท็บ **"จำลองหน้าจอ Signage"** (Tab 5 - หน้าจอ LED ต้อนรับ) | `Test-05`: เมื่อทำเช็คอินสำเร็จ หน้าจอ LED Signage ต้องขึ้นป็อปอัปแสดงชื่อผู้เข้าร่วมคนนั้นทันที |
| **REQ-06** | **การสุ่มล้อหมุนนำโชค (Lucky Draw Engine)**:<br/>สุ่มรายชื่อผู้ชนะรางวัลเฉพาะคนที่ผ่านประตูแล้วเท่านั้น | ตาราง `lucky_draw_winners`<br/>(บันทึกประวัติการชนะสลากรางวัล) | `POST /api/v1/lucky-draw/spin` (คำนวณสุ่ม)<br/>`io.emit('luckydraw:spin')` (ส่งผลลัพธ์) | แท็บ **"จัดการข้อมูล (CMS)"** (ปุ่ม Spin) และ จอ Signage (วงล้อหมุน) | `Test-06`: สั่ง SPIN สุ่มรางวัล ตรวจสอบว่าผู้ชนะเป็น Guest และชื่อโดนตัดออกจากสระในการหมุนรอบถัดไป |

## 3. ขั้นตอนการควบคุมคุณภาพของตาราง (Maintenance Policy)
1.  **เมื่อมีการขอเปลี่ยนแปลงความต้องการ (Change Request)**: Systems Analyst (SA) ต้องแก้ไขแถวที่เกี่ยวข้องในตารางนี้ พร้อมทั้งระบุรหัสเอกสารการขอเปลี่ยนรุ่น (Change Control Number)
2.  **ก่อนการส่งมอบเวอร์ชันการผลิต (Release Auditing)**: ฝั่งควบคุมคุณภาพ (QA) ต้องทำการไล่ตรวจสอบทีละแถว (REQ-01 ถึง REQ-06) และเซ็นชื่อกำกับผลการรัน Test Case เพื่อยืนยันว่าการเปลี่ยนเวอร์ชันมีเอกสารรองรับสมบูรณ์ตามหลักเกณฑ์ ISO 9002
